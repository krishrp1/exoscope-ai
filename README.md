# ExoScope AI

**Discover Worlds Beyond Our Stars.**

ExoScope AI is a full-stack deep-learning project that classifies transit-like signals from NASA's Kepler telescope as **CONFIRMED** planet or **FALSE POSITIVE**. A 1D convolutional network is trained on real Kepler light curves; a FastAPI backend serves it; a Next.js "observatory" lets you explore the data, classify signals, watch training live and inspect the results.

It scores signals that are already known. It does not search for new planets and it has not discovered any. The approach is inspired by Shallue & Vanderburg (2018), the Google work that identified Kepler-90i; this project is an independent, much smaller re-implementation and made no such discovery.

## Results at a glance

Held-out test split: 626 signals on 512 stars the model never saw, 252 of them confirmed planets.

| Metric | Test | Validation |
|---|---|---|
| Recall (CONFIRMED) | 0.877 | 0.910 |
| Precision (CONFIRMED) | 0.884 | 0.882 |
| F1 (CONFIRMED) | 0.880 | 0.896 |
| PR-AUC | 0.940 | 0.954 |
| ROC-AUC | 0.960 | 0.975 |
| Accuracy | 0.904 | 0.923 |

Test confusion matrix (rows: dataset label; columns: prediction):

| | Predicted FALSE POSITIVE | Predicted CONFIRMED |
|---|---|---|
| **FALSE POSITIVE** | 345 | 29 |
| **CONFIRMED** | 31 | 221 |

These numbers are copied from `backend/artifacts/metrics.json`, which the training run writes. Training is seeded and reproduces them exactly on this machine (38 epochs, best at epoch 28, about 14 seconds on CPU). To check: `backend/.venv/bin/python -m backend.ml.evaluate` recomputes every metric from the saved model and fails if any differs.

Always guessing the larger class would score 0.597 accuracy on this split. See [Limitations](#limitations) before quoting anything.

## Data and provenance

| Data | Label used in the app | Source | Used for |
|---|---|---|---|
| KOI catalog: 9,564 signals with dispositions and transit ephemerides | **Original Kaggle data** | Kaggle [`arashnic/exoplanets`](https://www.kaggle.com/datasets/arashnic/exoplanets), the NASA Exoplanet Archive KOI cumulative table | labels, period / epoch / duration, metadata |
| Kepler long-cadence PDCSAP light curves for 3,546 stars (185 million brightness measurements) | **Additional genuine astronomical observations** | NASA Kepler mission, from the MAST archive's public S3 mirror | model input for training, evaluation and inference |
| Landing-page animation; test fixtures | **Synthetic demonstration data** | generated by code | illustration and unit tests only, never training or evaluation |

The Kaggle file is a table. It has **no light curves**, so they were fetched from MAST for a seeded random sample of its stars. Labels are the catalog's `koi_disposition`, unchanged. `CANDIDATE` rows are unresolved, so they are never used for training or evaluation; the app can still score them.

4,136 labelled signals (1,586 CONFIRMED, 2,550 FALSE POSITIVE) are split **by host star** into 2,902 train / 608 validation / 626 test. Full detail: [`docs/DATASET_REPORT.md`](docs/DATASET_REPORT.md).

## How it works

1. **Catalog.** Read each signal's period, mid-transit time, duration and label from the Kaggle table.
2. **Light curve.** Load the star's Kepler PDCSAP flux (cadences with a clean quality flag).
3. **Clean and segment.** Drop missing values; split at data gaps and quarter boundaries.
4. **Detrend.** Divide each segment by a moving median at least four transit durations wide.
5. **Clip and fold.** Remove upward outliers only; fold on the period so all transits align.
6. **Bin.** Median-bin into two 256-bin views: the whole orbit (global) and a zoom of ±4 durations (local). Scale each to median 0, deepest bin −1.
7. **Classify.** Standardize with statistics fitted on the training split only, then run the CNN.
8. **Explain.** Saliency, Integrated Gradients and occlusion for the predicted class.

Training and inference call the same function (`backend/ml/preprocessing.py: process_light_curve`).

### Model

```
Input (256, 2)
Conv1D(32, k=5) → BatchNorm → ReLU → MaxPool
Conv1D(64, k=5) → BatchNorm → ReLU → MaxPool
Conv1D(128, k=3) → BatchNorm → ReLU
GlobalAveragePooling1D → Dense(64, ReLU) → Dropout(0.3) → Dense(2, softmax)
```

44,642 parameters. Adam (1e-3), sparse categorical cross-entropy, inverse-frequency class weights, early stopping and learning-rate reduction on validation loss, checkpoint on best validation loss, fixed seed. Training batches only are augmented (random time reversal, small noise).

**Leakage controls:** split by star; standardizer fitted on train only; augmentation and class weights on train only; no vetting-derived catalog column (`koi_score`, `koi_fpflag_*`, `koi_pdisposition`) reaches the model; the decision threshold was not tuned on the test split. Unit tests assert these.

More: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md), [`DECISIONS.md`](DECISIONS.md), [`docs/TALKING_POINTS.md`](docs/TALKING_POINTS.md).

## Setup

Requirements: Python 3.10 to 3.12 (TensorFlow has no stable build for 3.13+ on every platform; 3.12 is what this was built with), Node.js 20.9 or newer, about 2 GB of disk, and an internet connection for the data.

All commands run from the repository root.

### 1. Backend environment

```bash
python3.12 -m venv backend/.venv
backend/.venv/bin/pip install -r backend/requirements.txt
```

### 2. Data and model (about 25 minutes, mostly download)

```bash
scripts/setup_data.sh
```

This runs three steps, which you can also run one at a time:

```bash
backend/.venv/bin/python -m backend.ml.fetch_lightcurves   # Kaggle catalog + 3,546 light curves from MAST (~1.5 GB)
backend/.venv/bin/python -m backend.ml.preprocessing       # fold and bin into data/processed_views.npz (~35 s)
backend/.venv/bin/python -m backend.ml.train                # train and evaluate (~15 s on CPU)
```

The Kaggle dataset is public and downloads through `kagglehub` without credentials. If your environment requires them, set `KAGGLE_USERNAME` and `KAGGLE_KEY` or create `~/.kaggle/kaggle.json`. The fetch is resumable: rerun it if the network drops. To try the pipeline on less data, pass smaller counts, for example `--n-confirmed 150 --n-false-positive 300 --n-candidates 20`; metrics will differ.

Data and model weights are not committed (`data/`, `backend/saved_models/`, `backend/artifacts/` are in `.gitignore`).

### 3. Start the backend

```bash
scripts/start_backend.sh          # http://localhost:8000, API docs at /docs
```

### 4. Start the frontend (second terminal)

```bash
scripts/start_frontend.sh         # installs, builds and serves http://localhost:3001
```

Open <http://localhost:3001>. For development with hot reload use `cd frontend && npm install && npm run dev` instead.

### Configuration

Copy `.env.example` to `.env` to change backend settings; the frontend reads `frontend/.env.local`.

| Variable | Default | Meaning |
|---|---|---|
| `EXOSCOPE_CORS_ORIGINS` | `http://localhost:3001,http://127.0.0.1:3000` | Origins allowed to call the API and open the training WebSocket |
| `EXOSCOPE_MAX_UPLOAD_MB` | `10` | Upload size limit |
| `EXOSCOPE_MAX_UPLOAD_ROWS` | `500000` | Upload row limit |
| `EXOSCOPE_MAX_BATCH_SIZE` | `25` | Samples per batch prediction |
| `EXOSCOPE_LOG_LEVEL` | `INFO` | Backend log level |
| `EXOSCOPE_DATA_DIR`, `EXOSCOPE_MODELS_DIR`, `EXOSCOPE_ARTIFACTS_DIR` | `data`, `backend/saved_models`, `backend/artifacts` | Path overrides |
| `PORT` | `8000` | Backend port (`scripts/start_backend.sh`) |
| `NEXT_PUBLIC_API_BASE_URL` | `http://localhost:8000` | Where the browser finds the backend (set at build time) |

If you serve the frontend from another origin or port, add it to `EXOSCOPE_CORS_ORIGINS`.

## Using the app

| Page | What it does |
|---|---|
| Landing page | The idea in one screen, with an animated (synthetic, labelled) transit illustration |
| Overview | Dataset size, model status, test metrics, dataset health, recent predictions |
| Light Curve Explorer | Zoomable time-vs-flux plot for any signal, raw or normalized, with catalog-predicted transits shaded |
| AI Detection Studio | Classify a dataset signal, or upload a CSV light curve; see scores, the processed input, explanations and stage timings |
| Compare Signals | Two to four signals side by side or on shared axes, with synchronized zoom |
| Training Monitor | Start or stop a training run and watch loss, accuracy and learning rate arrive over a WebSocket |
| Model Performance | Test metrics, confusion matrix, ROC and PR curves, training curves |
| Dataset Explorer | Search, filter, sort and page through signals; open a target's detail |
| About & Methodology | Pipeline, architecture, attribution, limitations |

**Uploading a light curve.** CSV, TSV or whitespace-separated text, up to 10 MB, with a numeric flux column and ideally a time column in days. Give the period, mid-transit time and duration if you know them. If you leave them empty the backend estimates them with a Box Least Squares search and says so; that estimate can lock onto a multiple of the true period, and the result is less reliable.

**Training from the UI.** A completed run replaces the model that serves predictions, including a short run. To restore the documented model, run `backend/.venv/bin/python -m backend.ml.train` and restart the backend.

## API reference

Base URL `http://localhost:8000`. Interactive docs: `/docs`. Errors are always `{"error": {"code", "message", "details"}}`.

| Method and path | Purpose |
|---|---|
| `GET /api/health` | Liveness, model loaded, sample count, training state |
| `GET /api/dataset/stats` | Catalog, light-curve, split and health statistics, computed on request |
| `GET /api/dataset/samples` | List signals. Query: `search`, `disposition`, `split`, `sort`, `order`, `page`, `page_size` |
| `GET /api/dataset/samples/{id}` | One signal: light curve (`mode=raw\|normalized`, `max_points`), predicted transit times, metadata, folded views |
| `GET /api/model/status` | Trained or not, architecture, parameters, summary metrics |
| `GET /api/model/metrics` | Full test and validation metrics, curves, training history |
| `GET /api/model/plots/{name}` | Evaluation plots as PNG |
| `POST /api/predict` | Body `{"sample_id": "K00002.01"}` or `{"flux": [...], "time": [...], "period", "t0", "duration_hours"}` |
| `POST /api/predict/upload/inspect` | Multipart `file`: parse a CSV and report its columns and a suggested mapping |
| `POST /api/predict/upload` | Multipart `file` plus optional `time_column`, `flux_column`, `period`, `t0`, `duration_hours` |
| `POST /api/predict/batch` | Body `{"sample_ids": [...], "explain": false}`, up to 25 |
| `GET /api/predictions/recent` | Predictions since the server started |
| `POST /api/training/start` | Body `{"epochs", "batch_size", "learning_rate", "dropout", "augment"}`; 409 if a run is active |
| `POST /api/training/stop` | Stop after the current batch; the saved model is not replaced |
| `GET /api/training/status` | State, progress, latest values, history of the current run |
| `GET /api/training/history` | History of the last completed run and of the current one |
| `WS /ws/training` | Snapshot on connect, then `train_begin`, `epoch_begin`, `batch`, `epoch_end`, `checkpoint_saved`, `completed` / `stopped` / `error`, `finished`, plus heartbeats |

A prediction response contains `predicted_class`, `confidence`, `probabilities`, `ephemeris`, `processed` (the two views and the folded curve), `signal`, `warnings`, `explanation` (three attribution methods) and `processing` (measured milliseconds per stage).

```bash
curl -s -X POST localhost:8000/api/predict -H 'content-type: application/json' \
  -d '{"sample_id": "K00002.01", "explain": false}'
```

## Deploying

The frontend is a standard Next.js app and deploys cleanly to **Vercel**. The backend is a Python FastAPI app that needs a persistent host (it loads a TensorFlow model at startup, runs training jobs, and holds state) — **Railway**, **Render**, or **Fly.io** all work.

### Frontend → Vercel

```bash
vercel deploy
```

Or connect the repo to Vercel and set these environment variables:

| Variable | Value |
|---|---|
| `NEXT_PUBLIC_API_BASE_URL` | Your backend's public URL |
| `BACKEND_URL` | Your backend's public URL (used by `vercel.json` rewrites) |

`vercel.json` rewrites `/api/*` and `/ws/training` to the backend so the browser never hits a different origin during development.

### Backend → Railway

```bash
railway init
railway up
```

Or connect the repo to Railway. `railway.toml` sets the Python build, `uvicorn` start command, and CORS. The free tier gives 500 hours/month.

### Backend → Render

Connect the repo to Render using `render.yaml`. The free Starter plan includes a $100 credit and persistent disk for the light-curve data.

### Backend → Fly.io

```bash
fly launch
fly deploy
```

Fly machines run continuously, which is what the training manager needs.

### One-command local deployment

```bash
# Backend
scripts/start_backend.sh

# Frontend
scripts/start_frontend.sh
```

## Limitations

- **It classifies known signals.** It needs a period and timing. It does not detect new planets.
- **Labels are catalog dispositions, not ground truth.** "CONFIRMED" includes statistically validated planets, and some dispositions will be wrong.
- **It is trained on a sample:** 4,136 of the catalog's 7,197 resolved signals.
- **The sample is richer in planets than the catalog** (38% against 33%), because every signal on a fetched star is used and confirmed planets cluster in multi-planet systems. Precision would be lower at catalog prevalence.
- **31 of 252 confirmed planets in the test split are missed, and 29 false positives are called planets.** Kepler-2 b (HAT-P-7 b), a well-known hot Jupiter, is one of the misses.
- **Absolute depth is hidden from the model**, because each view is scaled to the same depth. Depth is a strong clue for eclipsing binaries.
- **One training run, one seed, no hyperparameter search.** There are no error bars, and validation loss is noisy from epoch to epoch.
- **A softmax score is not a calibrated probability**, and never the probability that an object is a planet.
- **Explanations describe the model**, not the sky. An attribution peak is not a detected transit.
- **Uploads without an ephemeris are less reliable.** The period estimate can be a multiple of the true period.
- **Detrending flattens a few signals entirely** (16 of 4,136) on highly variable stars, and partly flattens transits longer than about 1.5 days.
- **Kepler long-cadence data only.** Other instruments were not tested.
- Recent predictions are kept in memory and reset when the backend restarts. Model promotion after training is not atomic.
